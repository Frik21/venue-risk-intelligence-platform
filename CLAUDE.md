# Product Vision & Business Model

VenueGuard is the product name (still subject to change later, per direct product direction). The company behind it is **Vivarium** - surfaced today as a "Powered by Vivarium" attribution in the landing page's logo intro animation (`pages/landing.tsx`), the one place this is currently referenced in the app.

VenueGuard has two sides:

- **Management side**: the full admin app (Tasks, Quotes, Invoices, Clients, Vendors, Operator Database, Users, etc.) - used by Manager/Finance/Human Resources/Operations staff.
- **"Operators note"**: the CPO-facing field app (the Operational Canvas, at `/cpo`) - a separate product surface with its own branding, used by CPOs.

Going live, companies subscribe to one of two tiers:

- **Enterprise** - full Management-side access, up to 20 CPO seats allocated to Operators note.
- **Micro Enterprise** - Management-only access, up to 10 CPO seats.

Longer-term, **Operators note is also planned as a fully standalone downloadable product** for individual freelance CPOs to use entirely independent of the rest of the system - not tied to any company's subscription at all.

**This is why CPOs are treated as a completely separate, seat-limited pool from Management-side Users** (Admin/Manager/Finance/Human Resources/Operations, managed at `/admin/users`) - a CPO isn't an admin-managed role, they're inventory tied to a subscription tier, and eventually a product of their own. CPOs are onboarded and tracked via Operator Database instead of Users.

**None of the subscription/tier/seat-limit/billing/standalone-build mechanics exist yet** - no tier selection, no seat-limit enforcement, no billing, no standalone packaging. This section is confirmed product direction to design *around* and never contradict, not a spec to build from unprompted - treat it the same as the Product Constitution above: implement pieces of it only when explicitly asked, and if an unrelated task would conflict with this vision, STOP and flag it rather than deciding silently. Revisit as its own dedicated project when asked.

# Notes & Follow-ups

- **City/town database ceiling**: the search bar's city data (`city-registry.ts`) comes from Natural Earth's populated-places dataset, capped at 7,342 places worldwide - real cities and towns, but not exhaustive (e.g. Stellenbosch isn't in it). Come back to this later if we want a genuinely bigger database - likely means switching to a much larger source (e.g. GeoNames) and probably a real search backend instead of a static file shipped to the browser, since that kind of dataset is much bigger than what fits in a static array.
- **"Task Pending Quotation"**: on the Quotations page (`costs.tsx`), between the Quotes ledger and the Quotation Workspace - lists tasks with no formal Quote linked yet (`quotes.taskId` is null for that task). Its "Create Quote" button opens the Create Quote dialog pre-filled from the task (client/venue/requirements/dates/resources/manager), and the task drops off this list once that quote is saved.
- **"Vendors"**: now a full CRM (`/admin/vendors`) - onboard/track security subcontractors and suppliers, per direct product direction ("CRM style... onboard new security vendors"). Same structural pattern as Clients (profile card + dated activity log, detail page at `/admin/vendors/:id`) but deliberately without Clients' day/night rate or task/quote rollup fields - per direct product direction, a vendor is who VenueGuard pays/contracts with, not who it bills, so that CRM data model is a different shape. Schema: `vendors` + `vendor_activities` tables (`lib/db/src/schema/vendors.ts`, `vendor-activities.ts`).
- **"Communications"**: a real Manager-to-CPO broadcast (`/admin/communications`) - one-way, no chat, per direct product direction. Optionally task-connected: when posting, a Manager can pick a task from a dropdown (default "General - all operators"); picking one scopes the announcement to that task's roster (via `task_assignments`, the same roster-aware logic used by Tasks/Deployment/Schedule) - only CPOs on that task see it, shown with a `T-000x · title` badge. Leaving it "General" broadcasts to every CPO like before. Filtering happens frontend-side (`visibleAnnouncements` in `dashboard.tsx`, comparing each announcement's `taskId` against the current CPO's own task list). `announcements.taskId` is nullable with `onDelete: set null` (not cascade) so a message stays around as a general note if its task is later deleted. Completes pre-existing scaffolding already in the CPO Operational Canvas (`dashboard.tsx`) - its Communications panel (opened from the "Operators note" brand menu) previously showed hardcoded demo instructions, now shows real, roster-filtered announcements. Instructions also surface in the CPO's Alerts panel (`instructionAlerts`, mapped from the same filtered data) since a Manager instruction is exactly the kind of thing an operator shouldn't have to go looking for separately. Schema: `announcements` table (`lib/db/src/schema/announcements.ts`).
- **"Invoices"**: a real client-billing entity (`/admin/invoices`) - "money owed to you", per direct product direction. Own lifecycle (draft/sent/paid), separate from and simpler than Quotes - billing line items + a single tax rate, no markup or derived internal-cost build-up, since an invoice bills an already-agreed amount. "Task Pending Invoice" lists completed, non-invoiced tasks (same pattern as Quotations' "Task Pending Quotation") - its "Create Invoice" button pre-fills from the task, and from an approved Quote on that task if one exists. **Approving a Quote now auto-creates a draft invoice** (`routes/quotes.ts`'s PATCH handler, on the draft/sent→approved transition, guarded against duplicates by checking for an existing invoice with that `quoteId`) - a single uncategorized line item for the quote's `totalQuoteValue`, same client/tax/currency, per direct product direction. A Manager can then add further **categorized** line items on that draft for costs incurred beyond the quoted amount (operational costs, additional manpower, vehicles, etc.) - reuses Quotes' own cost category vocabulary (`COST_CATEGORIES`/`QUOTE_COST_CATEGORIES`, exported from `routes/quotes.ts` / `lib/api.ts`) so both entities share one taxonomy; `category` is nullable per line item (`null` = the original agreed amount, a real category = an added cost). Saving an invoice against a task marks that task `invoiced` server-side (same sync the auto-create path also triggers), which is what moves it from the Completed to Invoiced bucket on the Tasks list (see PATCH/POST `/invoices` in `routes/invoices.ts`). Schema: `invoices` table (`lib/db/src/schema/invoices.ts`), `lineItems` now `{category: string | null; description; amount}[]`. PDF via `lib/invoice-pdf.ts` (renders category as a `[Label]` prefix on the description).
- **"Payroll"**: now real CPO pay runs (`/admin/payroll`) - "money you owe operators", per direct product direction. Rolls up approved timesheet hours (same rate x hours math as Personnel Costs on the Quotations page - see `lib/personnel-cost.ts`) per operator into a "Pending Payroll" total; "Create Pay Run" snapshots that total into a `pay_runs` row (pending -> paid, "Mark Paid" stamps `paidAt`) and stamps every covered `timesheet_entries` row with that run's id (new `pay_run_id` column, `onDelete: set null`) so the same hours can never be paid out twice - deleting a run puts its hours back into pending. No currency label, matching Personnel Costs' existing convention (CPO rates don't carry their own currency). Schema: `pay_runs` table (`lib/db/src/schema/payroll.ts`).
- **Multi-office scoping**: Tasks, Quotes, Invoices, Clients, Vendors, and Users (Managers & CPOs) each carry an optional `officeId` FK to the pre-existing `offices` table, per direct product direction ("companies will have different offices... select an office and all the data from the allocated office"). A global switcher at the top of the Manager sidebar (`layout.tsx`, "All Offices" + one entry per office) is the single source of truth for which office is currently selected - persisted to `localStorage` and broadcast via a custom event so every page reacts without prop-drilling (see `lib/office-scope.ts`: `useSelectedOfficeId()`, `setSelectedOfficeId()`, `filterByOffice()`). Every list page (Tasks, Quotations' Quotes ledger, Invoices, Clients, Vendors, Users) filters to the selected office client-side; "All Offices" shows everything, including records with no office set (a record with `officeId: null` only ever shows under "All Offices", never implicitly claimed by any one office). Every creation dialog for these six entities (`new-task-dialog.tsx`, `quote-dialog.tsx`, `invoice-dialog.tsx`, `clients.tsx`'s `ClientDialog`, `vendors.tsx`'s `VendorDialog`, `users.tsx`'s `NewUserDialog`) defaults its own Office field to whatever's currently selected, editable per-record. `users.officeId` and `offices.managerId` reference each other, which needed an explicit `AnyPgColumn` return-type annotation on both `references()` callbacks (`schema/users.ts`, `schema/offices.ts`) to break a TS circular-inference error Drizzle otherwise can't resolve on its own. **Product surfaces still missing:**
- Real pricing + a payment processor (Stripe or similar) wired to actual subscription charges, with webhooks flipping `companies.status` (`trial`/`active`/`suspended`/`cancelled`) automatically instead of by hand - self-serve registration (see Notes above) creates a `trial` company but nothing ever moves it to `active` without the Owner doing it by hand on `/owner`
- Seat-limit enforcement - tiers already display "20 mgmt / 20 CPO" etc. but nothing currently blocks a company from exceeding it
- Ask Intelligence (CPO-side differentiator, deliberately deferred until there's cashflow for paid AI APIs) and Operational Route corridor analysis (the other CPO differentiator discussed, not yet built)

**Security/hardening before handling real customers' credentials:**
- Rate limiting on `/auth/login` and `/auth/register` - nothing currently stops brute-forcing a password or spamming fake companies into existence
- A real "forgot password" email flow - needs email sending infrastructure that doesn't exist yet (today's workaround is the Owner/admin manually generating one-time passwords)
- Basic security headers (`helmet` or equivalent) - not installed anywhere in the stack
- Database indexes on every table's `company_id` column - added as a filter everywhere this session, but with no index yet; cheap to add, matters as row counts grow per tenant

**Operational safety net:**
- Error tracking / uptime monitoring (e.g. Sentry) - a crash today is only visible if someone's watching logs
- CI running `pnpm run build`/typecheck automatically on every PR - none configured yet, all verification this session was manual
- Automated production database backups + a tested restore process - doesn't exist against any real database yet

**Business/non-code (not this repo's work, but blocking a real launch):**
- Registered business entity, Terms of Service, Privacy Policy
- Actual decided pricing for Enterprise vs Micro Enterprise (today's "Est. Monthly Revenue" figure on `/owner` is a hardcoded placeholder map, not real prices)
- A support channel for subscribers
- Hosting + a domain, connected together - mechanically simple once the above is far enough along (see this session's own walkthrough for the how-to)
